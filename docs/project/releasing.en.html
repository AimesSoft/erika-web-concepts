Releases and artifacts

Releasing and Artifacts

The release workflow builds the native erika_capi and Web / WASM prebuilt artifacts and attaches them to a GitHub Release. Each bundle contains the library files, erika.h, the MPL-2.0 license, and dependency notices. Desktop Linux is not released yet.

  • Platforms 6 native + Web
  • ZIP archives 15
  • Profile lgpl

Triggersトリガー#

Pushing a v* tag triggers an official release, which is published to GitHub Releases once the build finishes. A manual workflow_dispatch run only builds and does not publish; use it for pre-release checks. Before releasing, verify locally with the build process.

git tag v0.3.2
git push origin v0.3.2

The tag-triggered Release workflow performs the official build; a manual workflow run before tagging is not required.

Before you tag#

First set [workspace.package].version in the root Cargo.toml to the target version, then run cargo update -w and commit Cargo.lock together with it. The --locked build in CI requires the two to match. Leave the versions of vendored upstream dependencies unchanged.

Update the CHANGELOG and installation docs for the repository root, Flutter, and OHPM. Confirm that CI passes on the main branch, and complete the formatting, test, clippy, and Dart publish checks that the releasing documentation requires. At its entry point, the release workflow compares the tag version with the Cargo workspace version and fails immediately if they differ.

Later workflows sync the Flutter, OHPM, and Swift versions and native digests. After the GitHub Release completes, confirm the public versions on pub.dev, SwiftPM, and OHPM separately. A successful OHPM upload does not mean the review is complete.

Web / WASM archive#

liberika-web-0.3.1.zip is generated by cargo run -p xtask -- web build. It contains the JavaScript, two WASM modules, the Worker, licenses, build-manifest.json, and the index.html demo page. Its digest is written to SHA256SUMS together with the native ZIPs.

After extracting the archive completely, open it over HTTPS or localhost. A standalone static deployment is enough to play a local MKV file. The Web package is not yet published to npm. For integration and compatibility, see Web / WASM integration.

OpenHarmony OHPM packageOHPM パッケージ#

The native ArkTS package erika for OpenHarmony arm64 is distributed through OHPM and supports API 18 and later. As of 2026-10-30, 0.3.0 has passed review and is publicly available:

shell

ohpm install erika@0.3.0

The package contains the N-API bridge and a matching liberika_capi.so. For the API and the XComponent surface lifecycle, see the OpenHarmony package guide.

Bundle layout構成#

packaging/bundle.sh generates the C ABI bundles, and they all share the same layout:

<bundle-name>/
  lib/                    # Library files or xcframework
  include/erika.h         # C ABI header
  LICENSE                 # MPL-2.0
  THIRD_PARTY_NOTICES.md  # Dependency license notices and LGPL relink notes
  licenses/               # Full license text of each dependency
  MANIFEST.txt            # ref / commit / profile / build time

MANIFEST.txt records where the build came from: bundle name, git ref, commit, profile, and UTC time. Read it first when you trace an artifact's origin.

THIRD_PARTY_NOTICES.md describes the relink obligations for LGPL components. The library is distributed statically linked, so a host that switches to dynamic linking must be able to replace these components.

Consuming prebuilt artifactsプレビルト利用#

The Flutter plugin downloads the prebuilt runtime by default during its build (the pub.dev version of erika_flutter includes verification and caching). To build from source instead, export the following explicitly:

export ERIKA_FORCE_SOURCE_BUILD=1    # Build from source instead (ERIKA_REPO_ROOT must point to a repository checkout)
export ERIKA_PREBUILT_TAG=v0.3.1       # Custom prebuilt version tag; defaults to the current version

When you override ERIKA_PREBUILT_TAG explicitly, you must also set the matching ERIKA_PREBUILT_SHA256 for that archive; read the digest for your platform from SHA256SUMS in the same release. Building from source and using a custom prebuilt version are two independent configuration options.

The build scripts download the bundle for the platform from github.com/AimesSoft/liberika/releases/download/<tag>/, unpack it, and verify its digest against the release-level SHA256SUMS.

For a native host, unpack the bundle, use include/erika.h as the only header, and link the library in lib/ into the host. See C ABI integration.

Build and publish pipeline#

On main, the Release workflow builds each of these separately: two macOS architectures, three iOS slices, three tvOS slices, four Android ABIs, two Windows architectures, and OpenHarmony. Afterward it merges the universal binaries and XCFrameworks, or packages per ABI. The native dependency cache is saved per target and shared between CI and Release.

A release produces 15 ZIP archives in total: 9 C ABI archives, 4 Flutter Android runtimes split by ABI, 1 Swift XCFramework, and 1 Web / WASM package. SHA256SUMS records the digests of all archives.

After the native tag release succeeds, the Release ecosystem packages workflow updates the Flutter and OHPM versions and the native artifact digests, then publishes to pub.dev and OHPM. The Swift XCFramework build and the SwiftPM release proceed in parallel. After an OHPM upload succeeds, the platform review must still complete; the registry is the authority on the public version.

CI on the main branch selects native jobs based on the changed paths, and superseded builds on a branch can be cancelled. When a change touches only documentation or the ecosystem package publishing scripts, main CI skips the native build. Changes to native source, dependency patches, or the CI / Release build scripts still trigger it.
