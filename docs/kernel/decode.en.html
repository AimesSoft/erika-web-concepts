Hardware decoding

Decoding

Decoding is uniformly FFmpeg avcodec interface, through DecoderBackend Choose software or hardware backend. When the hardware path is unavailable, fall back to the software solution and switch to the VideoDecoderChanged Report the event to the host.

  • backend 7 kind
  • Hardware 6 / Software 1
  • Switch event VideoDecoderChanged

decoding backendデコーダ#

backendplatformDescription
Cuda / NVDECLinux / NVIDIAUse CUDA video decoding device.
VaapiLinux / Intel、AMDUse VA-API render device.
SoftwareallFFmpeg software decoding, fallback target for any platform.
VideoToolboxmacOS / iOS / tvOSApple hardware decoding.

MediaCodecAndroidsurface mode is the main mode and fails to fall back to ByteBuffer mode.
AvCodecHarmonyOSAVCodec hardware decoding, covering H.264 / HEVC.

The platform default selection is made by VideoDecodePreference Decision: Apple defaults to VideoToolbox, Windows defaults to D3D11VA, Android defaults to MediaCodec, HarmonyOS defaults to AVCodec, Linux defaults to try CUDA / NVDEC, and then VA-API; other platforms use software decoding.

Hardware pathハードウェア経路#

Hardware backend selection occurs in open_raw: Press the backend to select codec, after avcodec_get_hw_config Query the hardware configuration and then use av_hwdevice_ctx_create Create device context. Device creation failure will fall back along the fallback chain to software decoding.

MediaCodec is the most special path among them. Decoder binding in surface mode AVMediaCodecDeviceContext.native_window, and set ndk_codec=1、delay_flush=1、erika_nonblocking=1 Three options. When surface fails to be created or bound, the playback thread rebuilds the decoder in ByteBuffer mode and restarts. The entire process appears to the host once VideoDecoderChanged event.

Fallback is explicit. Publish on every backend switch VideoDecoderChanged event. The host can use it to update the diagnostic interface or just log. Statistical fields hardware_video_frames with software_video_frames Accumulate the number of decoded frames for the two paths respectively.

frame queueフレームキュー#

The decoded output enters a bounded queue, and the playback thread is decoupled from the rendering side queue. The queue depth can be found in PlayerConfig Medium adjustment:

QueueDefault capacityConfiguration fields
video frame3video_frame_queue_capacity
audio frame192audio_frame_queue_capacity
subtitle frame16subtitle_frame_queue_capacity

New frames are discarded when the queue is full, statistics field video_frame_backpressure_drops The cumulative number of discarded video frames. The audio frame queue is consumed by the audio clock, and the capacity is configured by PlayerConfig.audio_frame_queue_capacity decide (AudioSyncConfig Only synchronization parameters are included, not capacity).

Software decoding fallback#

0.2.1 Complete WMV / WMA software decoding, and support 8-bit and 10-bit AV1 through dav1d. When hardware decoding is unavailable or the video format is not supported by the device, software frames enter the same rendering pipeline; Windows also supports software frame upload.

Software decoding thread · 0.3.0#

Software video decoding enables frame/slice multi-threading by default, with the number of threads selected by FFmpeg based on the encoder and runtime environment. settings ERIKA_VIDEO_DECODE_THREADS=1 Restore single thread; use both when testing pure software paths ERIKA_HWDEC=software。

When the hard decryption backend internally returns to the software pixel format, the diagnosis and VideoDecoderChanged The actual decoding path, fallback reason, and count will be reported, and the actual hardware decoding cannot be determined solely by the requested backend.
