high dynamic range

HDR / EDR Output

liberika output encoding negotiated by the platform: Apple EDR, Windows HDR10 PQ, Android and Linux extended-linear scRGB. When negotiation fails, fall back to SDR. The fallback reason and counting time ErikaOutputStatus Report, not silently demote.

  • Output mode 4 kind
  • active coding 5 kind
  • Fallback reason 8 species (otherwise None Indicates no rollback)

Output modeMake an effort#

When the host created presenter ErikaPresenterConfig.output_mode Statement request:

modevalueDescription
Sdr0Fixed SDR output.
AppleEdr1Apple EDR, extended by headroom.
ExtendedLinear2extended-linear output (Android / Linux scRGB path).
Auto3Automatic selection based on content and surface capabilities.

The actual effective encoding is recorded in ErikaOutputStatus.active_encoding：SdrSrgb、AppleEdr、AndroidExtendedLinearScRgb、Hdr10Pq、LinuxExtendedLinearScRgb. The request mode and active encoding can be different, and the difference is the fallback.

Headroom Negotiationヘッドルーム#

The EDR and scRGB paths negotiate dynamic range based on the display's peak brightness. For host set_output_headroom Provides desired headroom with a flag indicating whether the renderer is capable of converging to usable values based on the surface's actual capabilities.

Status fields during negotiation:

  • requested_headroom — Host request value.
  • active_headroom / active_headroom_known — Current effective value and validity.
  • headroom_updates — Number of changes to the effective value.
  • extended_linear_frames — Number of frames output with extended-linear encoding.

fallback_count Cumulative number of rollbacks,data_space_failures The number of failed negotiations data space is accumulated individually. The host can use these two items to determine whether the HDR support of the target device is stable.

Android scRGB requires Vulkan, RGBA16F surfaces and the correct native window data space; Linux scRGB requires FP16 extended-linear WSI. Ordinary SDR surface uses tone mapping output.

Tone Mapping and Dolby Vision#

Starting from 0.2.0, BT.2390 EETF is used by default, and peak compression is completed in the IPT color space. Operators such as spline, BT.2446a, ST 2094, Mobius, Reinhard and clip are optional; black point and target contrast also participate in mapping.

Dolby Vision RPU supports piecewise / MMR reshaping and nonlinear matrix transformation, Profile 5 / 8 is processed as BT.2020 / PQ. Profile 7 uses the base layer and its mapping, and the enhancement layer residuals have not yet participated in the synthesis. The rendering conversion is performed here, instead of transmitting the Dolby Vision signal transparently to the display.

HDR10 software frames can be peaked using frame-by-frame brightness statistics, and perceptual gamut mapping LUT is built in the background by CPU and cached across frames. Apple EDR output updates with monitor headroom; P010 uploads retain 10-bit accuracy.
