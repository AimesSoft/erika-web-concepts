アーキテクチャの概要

Architecture

liberika は Rust によって実装されます。 demux から GPU レンダリングへのデコード、オーディオ、字幕、弾幕はすべてカーネル内で完了します。ホストはレンダリング サーフェスを提供し、再生コマンドを送信しますが、レンダリング パイプラインには参加しません。

  • コア crate crates/erika
  • C ABI 層 crates/erika_capi
  • めねじ 5
  • バックエンド trait 3

倉庫の階層化構成する#

パス責任
crates/erikaコア再生ライブラリ。 Player、Presenter、レンダリング バックエンド、オーディオ、字幕、弾幕。
crates/erika_capiC ABI エクスポートレイヤー。すべてをエクスポートする include/erika.h が勝つだろう。
crates/erika_ffmpeg_sysFFmpeg bindgen バインディング。
packages/erika_flutterFlutter プラグイン、macOS / iOS / tvOS / Windows / Android / HarmonyOS をカバーします。
packages/erika_ohosスタンドアロン OpenHarmony ArkTS / OHPM ネイティブ SDK、提供 ErikaPlayer XComponent surface bridgeと。
examples/検証、スモーク、デモプログラム。macos_native_demo、windows_native_demo はエンドツーエンドの例です。
xtask/ネイティブの依存関係ビルド オーケストレーション。deps plan / fetch / status / build。

モジュール分割モジュール#

crates/erika/src/ 以下のモジュールは役割に応じて分割されており、プラットフォーム関連のコードは次のように分割されています。 #[cfg(target_os = …)] ゲートされた、集中した apple.rs、windows.rs、android.rs、ohos.rs およびそのサブディレクトリ。

モジュール責任

playback再生ステートマシン、オーディオマスタークロック、フレームスケジューラ、VideoDecodePreference。
presenterPresenterRuntime。文字列 player、renderer、audio、overlay、作成者 render_tick ドライブ。
ffmpegdemux、decode、resample、seek。DecoderBackend 5 つのバックエンドの選択と構成。
audioAudioOutputBackend trait、f32 PCM ring buffer、オーディオクロック。
renderermetal（Apple）、d3d11（Windows）、wgpu(Android、HarmonyOS) バックエンド;pipeline tone map を使用して、バックエンドに依存しない色の決定を行います。
subtitleSRT / WebVTT / ASS 解析および libass レンダリング、埋め込みおよび外部字幕トラック。

データフローデータフロー#

再生チェーンはメディア ソースから始まり、レンダリング サーフェスで終了します。

playback data flow

MediaSource (file / HTTP range)
  → demux (ffmpeg)
  → decode (DecoderBackend: hardware / software)
  → frame queue (video / audio / subtitle)
  → PresenterRuntime::render_tick(host_time)
  → RenderFrameContext { media_time, overlay, danmaku, output_size }
  → RendererBackend::render_current_frame
  → surface (Metal / D3D11 / wgpu)

ステータスとイベントは独立しています crossbeam channel。プレーヤーのステータスの変更、継続時間、トラック、バッファリング、エラー、その他の情報がイベント チャネルとホストに公開されます。 poll_event または、Rust 側のイベント サブスクリプションの消費。

タイムベース。 オーディオ出力はマスタークロックです。ビデオ レンダリングは、vsync によってオーディオ クロックを調整するために量子化されます。詳細については、を参照してください。クロックとスケジューリング。

ねじ切りモデルスレッド#

カーネルは内部で 5 つの常駐スレッドを維持し、一部のプラットフォーム オーディオ出力はシステム コールバック コンテキスト (CoreAudio コールバック、WASAPI render スレッド) で実行されます。

スレッド名責任
erika-playbackコマンドループ。消費 PlaybackCommand、インラインビデオデコード、管理ステートマシン。
erika-demuxdemux コンシューマ スレッドは、bounded パケット キュー (容量 512) を playback スレッドに配信します。
erika-danmaku弾幕planが発生する。 Mutex + Condvar はモデルをリクエストし、結果は unbounded channel 経由で返されます。
erika-upscaler-buildArtCNN ウェイトロードとバックエンド構築 (Metal パス)。
erika-wasapi-renderWindows WASAPI オーディオ出力スレッド。

ホスト スレッドとカーネルの間の境界は、C ABI レイヤーによって制限されます。handle は内部同期を提供せず、複数のスレッドから同時に呼び出すことはできません。

3つの入り口エントリポイント#

liberika は、ホスト言語とレンダリングの所有権によって区別される 3 つの使用グループを公開します。

入口ホスト所有権をレンダリングする説明
PlayerRustホストがフレームデータをプルするRust API を完了します。イベントのサブスクリプション + ビデオ/オーディオ/字幕フレームのサブスクリプション。
ErikaHandleC / Swift / Dart FFIホストがフレームデータをプルするpullモデル。ホストはレンダリング ループ自体を管理します。
ErikaPresenterHandleC / Swift / Dart FFIカーネルホスティングpushモデル。ホストはサーフェスを提供し、フレームごとにそれを呼び出します render_tick。

3 セットの入口は同じ内部実装を共有します。 C ABI レイヤーのエクスポートされた各関数は、 catch_unwind パッケージ、panic のマップ先 ErikaStatus_Panic、FFI境界を超えません。

バックエンドの抽象化抽象化#

プラットフォームの違いは 3 つの trait の後に収束し、presenter とレンダー ループはプラットフォームに依存しません。

  • RendererBackend(core.rs) - 表面の取り付けとサイズ設定、render_current_frame、upload_player_frame、スクリーンショット。 Metal、D3D11、wgpu の 3 つの実装があります。
  • AudioOutputBackend(audio.rs) - 設定、再生制御、push(PcmAudioFrame)、時計のスナップショット。 CoreAudio / AudioQueue / WASAPI / AAudio / OHAudio の実装。
  • DecoderBackend(ffmpeg.rs) - ソフトウェア、VideoToolbox、D3D11VA、MediaCodec、AVCodec の 5 つのデコード バックエンド。

選択ルール:RendererBackendPreference(プラットフォーム ネイティブまたは wgpu フォールバック) レンダリング バックエンドを決定します。VideoDecodePreference デコード バックエンドはデフォルトでプラットフォームによって選択されます。

ブラウザ バックエンド · 0.3.0#

Web は独立した JavaScript Player インターフェイスです。 FFmpeg WASM は Worker で読み取りとカプセル化解除を行い、圧縮されたパッケージは WebCodecs、libass、および Rust に渡されます。 DFM エンジンは字幕と弾幕を処理し、次に WebGL2合成; Web Audio は出力および再生クロックを提供します。ネイティブ Presenter C ABI は使用されず、デスクトップ HDR または ArtCNN も含まれません。導入とサポートの範囲については、「」を参照してください。Web / WASM アクセス。
